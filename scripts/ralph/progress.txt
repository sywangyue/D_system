## Codebase Patterns
- Tailwind CSS 4.x uses CSS-based config: `@theme` block in `globals.css`, NOT `tailwind.config.js`
- Semantic color tokens in @theme use `--color-<name>` prefix → generates `bg-<name>`, `text-<name>`, etc.
- Layout spacing tokens in @theme use `--spacing-<name>` prefix → generates `w-<name>`, `p-<name>`, etc.
- SVG sprite sheet goes in `public/icons.svg` with `<symbol>` elements; reference via `<svg><use href="/icons.svg#id"/></svg>`
- Supabase migration files go in `supabase/migrations/` named `YYYYMMDDHHMMSS_init.sql`
- RLS policies use a `get_user_role()` helper function reading `auth.jwt() -> 'app_metadata' ->> 'role'`
- SQLite→PostgreSQL: `AUTOINCREMENT`→`BIGSERIAL`, `datetime('now')`→`NOW()`, date fields→`DATE` type
- Supabase SSR v0.10+ uses `getAll`/`setAll` cookie methods — `get`/`set`/`remove` are deprecated
- Server client: `createServerClient(url, key, { cookies: { getAll, setAll } })` with `cookies()` from `next/headers`
- Middleware client: same API but `getAll` reads from `request.cookies` and `setAll` writes to response
- Browser client: `createBrowserClient(url, key)` — cookies are handled automatically
- Database type structure: `{ public: { Tables: { table_name: { Row, Insert, Update } } } }` for use with `supabase.from<"table">()`
- When adding a new table, update BOTH the migration file AND the Database type in lib/types.ts
- Next.js 16 warns that "middleware" file convention is deprecated in favor of "proxy" — but both work for now
- The Database type in lib/types.ts is the single source of truth for TypeScript ↔ PostgreSQL schema mapping
- supabase-js `GenericSchema` constraint requires `Tables` entries to have `Relationships` field AND the schema must include `Views` + `Functions` fields. Manually-defined types don't satisfy this unless all fields are present. Workaround: omit the Database generic from createClient and use explicit type assertions on query results. Once a Supabase project is connected, run `supabase gen types typescript` to auto-generate a compatible Database type.
- Next.js API route handlers should use `Request` (not `NextRequest`) as parameter type for testability. Use `new URL(request.url).searchParams` instead of `request.nextUrl.searchParams`.
- Mock `next/headers` and `@supabase/ssr` in tests using `vi.mock()` BEFORE importing route handlers.
- Admin client (`lib/supabase/admin.ts`) uses service_role key — for `auth.admin.listUsers()` and similar admin-only Supabase calls
- API routes MUST do their own auth/RBAC via `supabase.auth.getUser()` — middleware only protects page routes, not `/api/*` paths
- When a route uses both server (anon) and admin (service_role) clients, mock `@/lib/supabase/admin` separately with `vi.mock("@/lib/supabase/admin", ...)`
- Test mock `createServerClient` should NOT use counters to distinguish admin-vs-user clients — mock admin via its own module instead
- Pages using `useSearchParams()` must split into two files: server component wrapper (`page.tsx`) with `<Suspense>` + separate client component (`*-content.tsx`) with the hook. This is a Next.js App Router requirement — `useSearchParams()` needs a Suspense boundary.
- Dashboard page data flow: initial mount fetches unfiltered API data for filter options derivation, then fetches with URL params for display. Subsequent filter changes only fetch filtered data. Use `useRef` to gate the filter-change effect from firing on mount.
- Client-only libraries (react-big-calendar, react-leaflet) must use `next/dynamic` with `{ ssr: false }`. Import the library's CSS in the dynamically-imported wrapper component, not in the parent or layout.
- API endpoints that need joined data from another table use Supabase's embedded resource select syntax: `.select("*, foreign_table(column1, column2)")`
- Server-side geocoding without external API: use a static `Record<string, [number, number]>` mapping known location names to lat/lng coordinates. Include substring/contains fallback for partial matches. Return a sensible default (e.g. center of China [35, 105]) for unknown cities.
