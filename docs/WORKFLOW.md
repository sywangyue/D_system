# 多模型协作流程 · V2-18 → V2-20

本文件定义 UI 重做与项目归档这三轮改造的**分工、交接契约与验收门禁**。
任务编码与进度在 `ROADMAP.md` / `HISTORY.md`，这里只讲「谁做什么、怎么交接、怎么算过」。

---

## 1. 这三轮改造的性质

**数据模型不动，HTML 结构基本不动。** 现有架构已经满足需求，归档是「把内容整理成
现有架构吃得下的形式」，不是「改架构去迁就内容」。三轮的重心是 **CSS + 交互细节**，
外加补齐展示能力上的缺口。

典型缺口长这样：知识库正文**已经支持图片**（`urlTransform` + `rewriteAsset` 会把
`![](images/x.png)` 改写到 `public/knowledge/<slug>/images/`），但 `prose-cjk` 里
**没有任何 `img` / `figure` 样式** —— 图片插进去是浏览器默认样式，超宽撑破容器、
没有圆角边框图注间距。**能力有，样式没做**，这类才是要补的。

### 顺序的一处调整

原设想是 设计 → 深度设计 → 筛选项 → 归档。唯一要动的是：**归档不能全排在最后**。

理由是数据量。`opportunity` 现在 1 条、`opportunity_event` 0 条 —— 空表上做出来的
布局，灌进真实数据后（长公司名、多标签、时间线堆叠、分页排序）大概率不成立。
所以**看板的深度设计要在真实数据进来之后做**；落地页不受影响，可以立刻开工。

## 2. 角色分工

| 角色 | 做什么 | **不做什么** |
|---|---|---|
| **Claude Code** | 架构决策、数据模型、交接规格、质检与返工单、安全与数据安全兜底 | 不做审美判断；不代替 DS 写业务代码 |
| **DeepSeek** | 全部代码改动：组件、接口、迁移、把设计稿翻译成令牌 | 不定视觉方向；不自行改数据模型 |
| **Stitch** | 第二轮初步设计：版式、层次、密度的多个方案 | 不出最终稿；不碰令牌命名 |
| **Claude Design** | 深度设计：细节、状态、动效、最终视觉规范 | 不直接改仓库代码 |
| **Max** | 视觉拍板、内容决策、归档录入 | — |

### 质检规则（沿用既有约定）

- **DS 做，Claude 质检。** 不合格时写返工单交回 DS，不给代码。
- 同一问题 **DS 两次没改对，Claude 接手**，并在 commit 里写清原因。
- **安全类与数据丢失类缺陷不走两次规则，Claude 立即修** —— 路径穿越、误删列、写错库，
  多一轮往返就可能带上线。
- DS 发现规格有错，以 DS 为准先记录，由 Claude 判定后改规格。

## 3. 交接契约

### 3.1 给设计工具的输入（Stitch / Claude Design）

设计工具不知道本项目的令牌体系，**不给这三样就必然产出无法落地的稿子**：

1. **令牌清单** —— `app/globals.css` 里的 CSS 变量名与实际值。别手抄，实时导出：

   ```bash
   awk '/^[[:space:]]*--/ {gsub(/^[[:space:]]+/,""); print}' app/globals.css | sort -u
   ```

   令牌会随设计演进变化，**每次开新一轮设计前重新导出一次**，不要复用上一轮的清单。
2. **三条硬约束**（见 §3.3），必须写进给设计工具的 prompt
3. **现状截图** —— 要改的页面当前长什么样，以及真实数据的极端样本（最长的公司名、标签最多的行、空状态）

### 3.2 设计稿 → 代码

设计稿产出的是 **HTML/CSS**，不能直接进仓库。交接物是一份**视觉规格**，DeepSeek 照它翻译：

```
每个改动点写成三行：
  位置：  哪个组件 / 哪一块
  意图：  要达到什么视觉效果（层次、密度、对比）
  令牌：  用哪几个现有令牌实现；需要新令牌时给出名字与值，并说明为什么现有的不够
```

**不接受「把这里改好看点」这类交接。** DeepSeek 看不到审美，模糊指令必然翻译错。

### 3.3 三条硬约束（设计与代码都适用）

| 约束 | 门禁命令 |
|---|---|
| 无硬编码色值 | `grep -rnE '#[0-9a-fA-F]{3,8}' app/ components/ --include="*.tsx" \| grep -v '//\|\*'` 应为空 |
| 无 Tailwind 内置灰 | `grep -rn 'text-gray-\|bg-white\|bg-gray-' app/ components/` 应为空 |
| 界面不碰品牌橙 | `grep -rn 'color-brand' app/ components/ --include="*.tsx"` 只应命中 `BrandLockup.tsx` |

> 第一条的 grep 会把注释里的色值也算进去（当前 7 处命中全是注释），所以加了过滤。

## 4. 四个阶段

### 阶段 A · 落地页设计 + 展示缺口盘点（并行）

落地页不依赖任何业务数据，可以立刻开工；盘点同时进行，为阶段 B 定规格。

**A1 落地页视觉**（Stitch → Claude Design → DeepSeek）
- 范围：`app/page.tsx` + `components/landing/` 下 8 个组件
- 落地页是对外第一屏，也是业务汇报时最先打开的页面，优先级最高

**A2 展示缺口盘点**（Claude Code）
- 输入：Max 挑出要上传的内容，给一两份样本
- 输出：缺口清单 —— 这些内容在现有页面上显示出来还缺什么样式或组件
- **数据模型不动**：现有表够用，不加「人/联系人」表，不为归档改 schema

**验收**：落地页过三条门禁 + `npm run build` 无告警；缺口清单经 Max 确认

---

### 阶段 B · 展示能力补齐（DeepSeek 主力）

**B0 组件收敛 —— 必须最先做**

当前 `Tag` 定义 8 份、`Pill` 4 份、`Empty` 4 份，分散在 16 个文件里。
不先收成共用组件，后面每改一次配色就要改 16 处。这是纯机械改动、与审美无关，
是 DeepSeek 的标准活。

**B1 补展示缺口** —— 按 Max 实际要上传的内容清点，缺什么补什么。已确认的第一项：
知识库正文的图片样式（`img` / `figure` / `figcaption` 在 `prose-cjk` 里完全缺失）。

**B2 导入通道** —— 用现有脚本，不做上传界面：
- 文档 → 放进 `reports/` → `scripts/index_resources.py` 建索引 → `scripts/backfill_reports.py` 抽正文入 `intel_report`
- 知识库 → `knowledge/<slug>/index.md` + 图片放 `public/knowledge/<slug>/images/`
- 公司名单 → Excel 批量导入脚本，字段映射照 A2 的清单，参考 `tools/import_tags.py` 的写回模式

> 这三条通道的后端**已经存在，或只差一个脚本**。唯一使用者是 Max 本人，跑脚本完全够用，
> **不要为了「能在界面上传」去造上传端点** —— 那是一整套路径校验与权限设计，
> 收益只是省下一条命令。真要做，等归档完成、确认是高频动作之后再说。

**安全红线**（Claude Code 直接把关，不走两次规则）：
- 任何按路径读文件的端点，校验必须在字符串层完成，杜绝 `../` 穿越 —— 参照 `app/api/resource/[id]/download/route.ts` 里的 `resolveSafe`
- 内容文件落 `reports/` 或 `knowledge/`；**除知识库图片外不要往 `public/` 放东西**（`public/` 不经中间件，等于对全网公开）
- 写库走 `getWritableDb()` 并 `finally` 关闭；改阶段与写 `stage_change` 同事务

**验收**：Max 能把一份真实文档和一份真实名单灌进去，页面上正常显示（图片不撑破、表格不串行）

---

### 阶段 C · 项目归档（Max 主力）

把手头内容整理成现有架构吃得下的形式，灌进平台。这是最重的一步，但重在整理、不在开发。

**改库前一律备份**：`cp data/mwlab.db data/backups/mwlab_pre-归档-$(date +%Y%m%d).db`

**验收**：数据量达到能暴露布局问题的规模（公司数百条、机会数十条、文档数十份），
`docs/QC.md` §2 基线同步更新到新数字

---

### 阶段 D · 数据看板设计 + 筛选项

**在真实数据之上做**，这是把它排在归档之后的全部理由。

**D1 看板视觉**（Stitch → Claude Design → DeepSeek）—— 盘面、机会台、公司库、调研库
**D2 筛选项与表头** —— 此时才知道真实数据的分布，才知道该筛什么、哪列该上表头

> 筛选项排在设计之后：先有版式，才知道筛选器放哪、占多少空间。
> 反过来做会出现「筛选器设计好了但版式容不下」。

**验收**：三条门禁 + `npm test` + `pytest` 全绿；Max 实际使用一周没有想改的布局

## 5. 每轮必过的通用门禁

任何一轮改动合并前，四条全过：

```bash
npx tsc --noEmit                 # 类型
npm run build                    # 构建 —— Turbopack 告警也算失败
npm test                         # vitest
python3 -m pytest tests/ -q      # pytest
```

加上 §3.3 三条视觉约束，以及 `docs/QC.md` §2 的数据基线对照。

---

## 6. 什么情况下停下来

- **设计稿要求的效果现有令牌做不到** → 先定令牌，别让 DeepSeek 临时硬编码
- **归档时真的发现字段装不下** → 停下来定模型，不要往 `notes` 里塞 JSON
- **同一个问题 DS 改了两次还不对** → Claude Code 接手
- **任何涉及删列、改主键、批量 UPDATE 的动作** → 先备份、先出 dry-run、先给 Max 看变更条数
